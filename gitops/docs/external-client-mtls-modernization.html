External client mTLS modernization

Replace coordinated annual leaf-certificate exchanges with CA-based trust, automated renewal, stable workload identities, and independent rotation.

Executive summary

The current certificate process requires the Artemis team and each external client team to exchange and install new leaf certificates on a coordinated annual schedule. This process consumes engineering time and can cause outages when either side misses a step or changes a certificate without sufficient overlap.

This design moves trust from individual leaf certificates to approved issuing certificate authorities (CAs). Artemis trusts each approved external client CA. External clients trust the CA that issues the Artemis server certificate. Each side then renews its own leaf certificate independently.

Primary outcome Independent renewal

Routine leaf-certificate renewal does not require a truststore update by the other party.

Authorization model Stable identity and role

Artemis maps a stable certificate identity to least-privilege send and consume roles.

Recommended automation Vault or enterprise PKI

Clients obtain and renew certificates through an automated workload-bound process.

Expected result: Annual leaf-certificate changes become routine automated renewals. Coordination is required only for infrequent CA-chain changes or identity-policy changes.

Problem

The current process pins individual client and server certificates. A leaf certificate change therefore changes trust configuration on both sides:

  • The external client sends its replacement certificate to the Artemis team.
  • The Artemis team adds the certificate to the broker truststore.
  • The Artemis team sends the replacement broker certificate to the external client.
  • Both teams schedule deployment and validation before either old certificate expires.

This process has several failure modes:

  • A certificate expires before deployment finishes.
  • One party installs the wrong environment certificate or an incomplete chain.
  • The subject identity changes and no longer matches broker authorization.
  • The old certificate is removed before every client instance reloads the new certificate.
  • A truststore update requires a broker or client restart during a limited maintenance window.

Goals and non-goals

Goals

  • Remove coordinated annual leaf-certificate exchanges.
  • Automate certificate issuance, renewal, distribution, and reload.
  • Preserve mutual TLS (mTLS) and least-privilege Artemis authorization.
  • Support external clients that use OpenWire, AMQP, or STOMP.
  • Support staged migration without an outage.
  • Provide revocation, expiration monitoring, and auditable workload identity.

Non-goals

  • Require every external organization to use the platform Vault deployment.
  • Trust every certificate issued by a broad enterprise CA without additional identity checks.
  • Replace all messaging protocols during the certificate migration.
  • Store client private keys in Git, Helm values, or the Artemis broker.
  • Use the Hawtio human-login design for application messaging clients.

Recommended decision

Adopt CA-based mTLS with automated leaf renewal

Configure Artemis to trust approved external client issuing CAs. Configure external clients to trust the approved Artemis server issuing CA. Map each stable client certificate identity to an Artemis application role. Use pinned leaf certificates only when an issuing CA is too broad, cannot meet policy, or cannot provide reliable revocation.

Identity granularity

Assign one logical identity to each application and environment. Do not assign a separate identity to every producer object, consumer object, connection, or thread.

Multiple replicas can use certificates that represent the same logical application identity. A certificate automation system can issue a unique key and serial number to each replica while retaining the same approved identity.

Trust granularity

Prefer a dedicated messaging-client intermediate CA for each organization or trust boundary. If only a broad enterprise CA is available, combine CA trust with an exact or narrowly matched certificate identity allowlist in Artemis.

Trust model

Transport trust and messaging authorization remain separate controls. Passing the TLS handshake does not grant permission to send or consume messages.

Client-to-broker trust

  1. The client presents its leaf certificate and intermediate chain.
  2. Artemis validates the chain against the external client trust bundle.
  3. Artemis validates expiration and revocation status.
  4. JAAS maps the stable identity to an application role.
  5. Artemis applies destination-level send and consume permissions.

Broker-to-client trust

  1. Artemis presents its server certificate and intermediate chain.
  2. The client validates the chain against its server trust bundle.
  3. The client verifies that the DNS name matches a certificate subject alternative name.
  4. The client establishes the TLS connection.

Security boundary: Do not grant an Artemis role solely because a certificate chains to an enterprise CA. Require an approved workload identity and a least-privilege role mapping.

External client changes

Most clients need configuration and certificate-lifecycle changes, not application business-logic changes.

Required external client capabilities
Capability Required change Operational effect
TLS endpoint Connect to the external mTLS listener. Use an SSL OpenWire endpoint, an amqps:// endpoint, or TLS-enabled STOMP. The client uses encrypted transport and presents a client certificate.
Client key material Provide a leaf certificate, private key, and issuing chain in PEM, JKS, or PKCS#12 format. The client proves its workload identity during the TLS handshake.
Server trust Trust the Artemis server issuing CA instead of the current Artemis leaf certificate. Artemis can renew its server certificate without a client truststore update.
Automated issuance Use Vault Agent, cert-manager, an enterprise certificate agent, or another approved enrollment process. The client receives a replacement certificate before expiration.
Reload or restart Reload the TLS context, recycle the connection pool, or perform a rolling restart after renewal. New connections use the replacement certificate before the old certificate expires.
Monitoring Report certificate expiration, renewal failure, and the active certificate serial number. Teams can correct failures before they affect connectivity.

Client implementation patterns

Recommended automation by runtime
Runtime Recommended pattern Typical application change
Kubernetes Use cert-manager with an approved Vault or enterprise issuer. Generate PKCS#12 or JKS output when the Java client requires it. Mount the generated Secret and add a rolling restart or TLS reload trigger.
Virtual machine Use Vault Agent or an approved enterprise certificate agent to write the certificate and key to a protected path. Configure keystore paths and a reload command or service restart.
External partner platform Use the partner's enterprise PKI. Share only the approved issuing CA chain and expected stable identity with the Artemis team. Automate renewal within the partner platform and reconnect after renewal.
Legacy appliance Use vendor-supported automation. If the appliance cannot automate renewal, evaluate an approved local TLS proxy. Point the appliance to the proxy or retain leaf pinning as a documented exception.

Illustrative Java client configuration

A Java client can often consume a renewed keystore without business-logic changes. Exact properties depend on the JMS client and protocol.

-Djavax.net.ssl.keyStore=/run/secrets/messaging/client.p12
-Djavax.net.ssl.keyStoreType=PKCS12
-Djavax.net.ssl.trustStore=/run/secrets/messaging/server-trust.p12
-Djavax.net.ssl.trustStoreType=PKCS12

Store passwords in the approved runtime secret mechanism. Do not place passwords or private keys in source control, startup logs, or connection URLs.

Lifecycle workflows

Routine client certificate renewal

  1. The certificate agent requests a replacement certificate before the current certificate expires.
  2. The issuer returns a new leaf certificate and chain with the same approved workload identity.
  3. The agent writes the new key material atomically.
  4. The client reloads its TLS context or performs a rolling restart.
  5. New connections present the replacement certificate.
  6. Monitoring confirms successful connections with the replacement certificate.

Artemis requires no truststore or role-mapping change because the issuer and stable identity did not change.

Routine Artemis server certificate renewal

  1. The platform certificate controller renews the Artemis server certificate.
  2. The server certificate retains the required DNS subject alternative names.
  3. The broker reloads the certificate or restarts one high-availability peer at a time.
  4. External clients validate the replacement certificate against the existing server CA trust bundle.

External clients require no truststore update because the trusted server CA did not change.

Issuing CA rotation

  1. Add the new CA chain to the trust bundle while retaining the old chain.
  2. Verify that Artemis and external clients accept both chains.
  3. Begin issuing new leaf certificates from the new CA.
  4. Wait until every workload uses the new chain and all old leaf certificates expire.
  5. Remove the old CA chain after the approved overlap period.

CA rotation remains coordinated, but it occurs much less often than leaf-certificate renewal and uses a planned dual-trust period.

Revocation

  1. Revoke a compromised or retired client certificate through its issuing CA.
  2. Update the certificate revocation list (CRL) or online certificate status protocol (OCSP) service.
  3. Remove or disable the corresponding Artemis identity mapping.
  4. Close active connections for the revoked identity when policy requires immediate termination.

Migration plan

The migration uses dual trust and does not require a shared cutover window.

  1. Inventory current identities

    Record each client protocol, endpoint, certificate subject, issuer, expiration date, application owner, and required send or consume permissions.

  2. Approve the issuing CA model

    Select a dedicated messaging intermediate when available. Document exceptions that require a broad enterprise CA or leaf pinning.

  3. Establish dual trust

    Add approved issuing CA chains while retaining all current leaf certificates and current authentication paths.

  4. Enable automated issuance

    Configure each client to obtain, store, renew, and reload its certificate without manual transfer.

  5. Migrate clients incrementally

    Move one client at a time to the external mTLS listener. Validate identity, authorization, reconnect, and failover behavior.

  6. Remove obsolete pins

    After all clients migrate and old leaf certificates expire, remove pinned leaf certificates and legacy credential paths.

  7. Exercise rotation

    Perform an early renewal and a planned dual-CA rotation test before production approval.

Artemis implementation

The repository already includes a configuration surface for TLS acceptors, client authentication, TLS Secret references, trust Secret references, per-acceptor security domains, and a mounted JAAS Secret.

Required broker configuration

  • Create a separate external mTLS acceptor and Service.
  • Set sslEnabled and needClientAuth to true.
  • Reference the Artemis server certificate through sslSecret.
  • Reference the external client CA bundle through trustSecret or the operator-compatible client truststore.
  • Assign an external certificate security domain.
  • Map stable client identities to roles in the externally materialized JAAS Secret.
  • Grant each role only the required address and queue operations.

Repository changes still required

  • Connect Vault, cert-manager, or the approved secret synchronization system to the operator-compatible TLS and JAAS Secret shapes.
  • Add per-listener NetworkPolicy source selection so external sources cannot reach unrelated client listeners.
  • Configure and validate TLS reload behavior or one-peer-at-a-time restart behavior.
  • Add CRL or OCSP configuration and failure-path tests.
  • Extend the validation client to mount a client keystore and truststore and to test mTLS without a username and password.
  • Provide the approved private external TCP exposure path.

Deployment boundary: The Artemis chart should store only Secret names and non-secret authorization policy. Private keys, certificate contents, certificate subjects, and rendered JAAS data must remain in the approved external secret system.

Risks and mitigations

Primary risks
Risk Impact Mitigation
Broad CA trust Unrelated enterprise certificates can complete the TLS chain validation step. Prefer a dedicated intermediate. Require an exact or narrow Artemis identity allowlist, NetworkPolicy restrictions, and connection limits.
Identity drift A renewed certificate uses a different subject and fails JAAS mapping. Define a stable identity profile and test renewal before production. Normalize distinguished names where supported.
Failed client reload The client keeps using an old certificate until expiration. Renew early, perform a rolling restart when hot reload is unavailable, and alert on the active certificate expiration date.
Incomplete certificate chain The peer cannot build a path to a trusted CA. Include the leaf and required intermediates in the presented chain. Test with a clean truststore.
Revocation gap A compromised certificate remains usable until expiration. Use short certificate lifetimes and configure the approved CRL or OCSP policy.
CA rotation ordering New leaves are issued before the peer trusts the new CA. Add the new CA first, verify dual trust, rotate leaves, and remove the old CA last.
Private key exposure An attacker can impersonate a client or broker. Generate keys within the workload boundary, restrict filesystem permissions, use short lifetimes, and never transfer private keys between teams.

Alternatives

Alternative approaches
Approach Assessment Recommendation
Continue leaf pinning Provides narrow trust but preserves annual exchange, deployment, and coordination work. Exception only
CA-based mTLS with automation Preserves protocol compatibility and removes routine cross-team renewal coordination. Recommended
SPIFFE and SPIRE Provides short-lived workload identities and streamed trust bundles. It requires compatible workload identity infrastructure and federation across organizations. Future evaluation
OIDC and short-lived tokens Can remove client-certificate lifecycle work for supported protocols. It requires token acquisition, client-library support, and a messaging authentication redesign. New AMQP clients
TLS proxy or gateway Can isolate certificate handling from a legacy application. It adds another security boundary and must preserve a trustworthy client identity for authorization. Legacy fallback

Acceptance criteria

The design is ready for production when tests demonstrate all of the following results:

  • An approved external client connects with a CA-issued certificate and no messaging username or password.
  • An unmapped certificate from a trusted CA fails Artemis authentication.
  • An untrusted, expired, or revoked certificate fails the connection.
  • A producer identity can send only to approved destinations.
  • A consumer identity can consume or browse only approved queues.
  • A routine client leaf renewal completes without an Artemis truststore or role-mapping change.
  • A routine Artemis server leaf renewal completes without an external client truststore change.
  • The client reloads or reconnects before the old certificate expires.
  • A dual-CA overlap test supports an issuing CA rotation without an outage.
  • Monitoring alerts before expiration and on renewal, reload, chain-validation, or revocation failures.
  • No private key or certificate password appears in Git, rendered manifests, command-line history, logs, or reports.

Open decisions

Issuing authority
Can the enterprise certificate team issue a dedicated messaging-client intermediate, or must Artemis trust broader enterprise intermediates?
Client inventory
Which external clients use OpenWire, AMQP, STOMP, or an appliance-specific library, and which clients support automated reload?
Certificate lifetime
What leaf-certificate lifetime and renewal window meet security policy and provide enough time to recover from renewal failures?
Revocation policy
Does the environment require CRL, OCSP, short-lived certificates, or a combination?
Secret delivery
Will the platform use cert-manager, Vault Agent, an external secret synchronization controller, or an enterprise certificate agent?
Identity field
Will authorization use a stable subject distinguished name, a subject alternative name URI, or another approved workload identifier?
External exposure
Which private load balancer, gateway, or network path will expose the external mTLS listener?
Legacy exceptions
Which clients cannot automate renewal and require temporary leaf pinning or a local TLS proxy?
